## Prisma no bundle da Vercel (causa raiz de "site no ar mas db down")

Sintoma: landing/login 200, `/api/health` → `db: down`,
`PrismaClientInitializationError` sem código, mensagem
`could not locate the Query Engine for runtime "rhel-openssl-3.0.x"`, `latencyMs` baixo.

Causa: o output file tracing do Next **não seguiu o symlink do pnpm** até
`node_modules/.pnpm/@prisma+client@*/node_modules/.prisma/client`, então a lambda foi
publicada sem `libquery_engine-*.so.node`. `binaryTargets` e `serverExternalPackages`
já estavam corretos — não era isso.

Correção (`apps/web/next.config.ts`):
```ts
outputFileTracingIncludes: {
  "/**/*": [
    "../../node_modules/.pnpm/@prisma+client*/node_modules/.prisma/client/**/*",
    "../../node_modules/.prisma/client/**/*",
    "./node_modules/.prisma/client/**/*",
  ],
}
```

Verificação local sem deploy: buildar e conferir
`apps/web/.next/server/app/api/health/route.js.nft.json` — os dois engines
(`debian-openssl-3.0.x` e `rhel-openssl-3.0.x`) precisam estar em `files`.

## E-mail: Gmail SMTP (EMAIL_USER/EMAIL_PASS)

- `packages/auth/src/mail.ts` agora tem `smtpMailer`, `smtpConfig`, `probeSmtp`.
  Precedência: `MAIL_TRANSPORT` explícito → SMTP (pares completos) → Resend → missing.
- Gmail: host derivado de `@gmail.com`, porta 465 (TLS implícito), From = conta.
  `EMAIL_PASS` precisa ser **senha de app** (16 chars), não a senha da conta.
- Bug real encontrado por teste: variável declarada vazia na Vercel chega como `""`,
  e `env.EMAIL_HOST ?? default` não cai no default. Usar `||` nesses casos.
- `nodemailer` marcado em `serverExternalPackages`; o Next acabou **inlinando** no
  chunk (não aparece em nft.json), e funciona — validado com `next start` real.
- Health expõe `smtp: { host, port, reachable }` via `probeSmtp` (TCP puro, sem auth).
  Resposta em produção: smtp.gmail.com:465 → reachable **true**: a Vercel não bloqueia
  SMTP de saída nessas portas.
- Teste de SMTP usa `smtp-server` (devDep) em porta efêmera: cobre EHLO/AUTH/DATA real,
  não mock do nodemailer.

## Migração falhando em produção (causa raiz)

`prisma migrate deploy` morria em `20260101000100_rls` com `42501 permission denied to
create role`: no Neon, `neondb_owner` não é superusuário nem tem CREATEROLE. Reproduzido
localmente com um papel `NOSUPERUSER NOCREATEROLE` dono do banco → erro idêntico,
inclusive com um schema `neon_auth` presente (que é irrelevante para a falha).

Consequência em cascata: a falha fica registrada em `_prisma_migrations` e todo deploy
seguinte para com P3009.

Correções:
- migração de RLS captura `insufficient_privilege` e condiciona GRANT/REVOKE à existência
  do papel; `ALTER DEFAULT PRIVILEGES` incluído (tabela nova nascia inacessível);
- `scripts/migrate-on-deploy.mjs` detecta P3018/P3009, roda `migrate resolve --rolled-back`
  e repete uma vez; reaplica os grants a cada build; `ALTER ROLE ... PASSWORD` é
  melhor-esforço;
- health agora reporta `migrations: "falhou"` + `migrationFailed` e só dá 200 com
  `aplicadas`.

Experimento do fluxo real (local, papel sem CREATEROLE): migrar sem o papel → NOTICE e
sucesso; criar `nextgen_app` como o console faria; rodar grants; conectar com ele →
`is_superuser=off`, `select count(*) from schools` = 0 (RLS falha fechada).

## Por que o site ficou fora do ar (cadeia completa)

1. `apps/web` usava `prebuild` para migrar. O build da Vercel é `turbo run build`, que
   executa só o script `build` — `prebuild` do npm nunca rodou. Nenhuma migração por build.
2. Alguém rodou `db:migrate` manualmente: 5 migrações aplicadas, 22 tabelas, e
   `nextgen_app` criado `NOLOGIN` (como a migração define).
3. Nada ligou o login. Prisma com papel NOLOGIN → P1001 "can't reach database server",
   mensagem que manda procurar host/TLS, onde não havia problema.
4. Mesmo com o passo no `build`, o `ALTER ROLE` falhou: Neon recusa a senha de
   `APP_DB_PASSWORD` com HTTP 400 "insecure password".

Diagnóstico que resolveu: health passou a (a) testar TCP por endpoint, (b) tentar
pooler/direto × app/dono com Prisma real, (c) consultar `pg_roles` e `_prisma_migrations`
como dono, (d) ler `deploy_log`. Com isso: dono conecta, app não; papel existe e
`can_login=false`; dono tem CREATEROLE; migrações 5/5.

Falta: trocar `APP_DB_PASSWORD` por uma senha forte na Vercel e redeployar (ou rodar
`alter role nextgen_app login password '<forte>'` no SQL Editor do Neon com o mesmo valor).
